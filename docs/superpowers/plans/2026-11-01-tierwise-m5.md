# tierwise M5 Implementation Plan: Eval Harness and Benchmark

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure tierwise's routers on cost vs. quality: a threshold sweep that gives the Pareto curve, compared with all-strong, all-cheap and random baselines. It produces the resume number (**cost saved at 95% of flagship quality**), a critical-misroute gate in CI, and `BENCHMARK.md`.

**Architecture:**
- **New package `evaluation/`** (offline, like `training/`):
  - **Datasets** turn into `EvalRow`s: one prompt, plus the quality and cost of a *cheap* and a *strong* model answering it.
  - **Scorers** give each prompt a routing score. There are four: random, rules, learned `p`, and the **deployed hybrid**. The hybrid runs the real `route()` pipeline, with rules first and learned when rules are unsure.
  - **The sweep** routes a prompt to the strong model when its score ≥ t, for every t, and turns each t into a (cost, quality) point.
- **Two datasets:**
  - **Headline:** our Apache-2.0 held-out split.
  - **Out-of-distribution:** SPROUT, downloaded at eval time and never committed.
- **Outputs:** JSON results and PNG plots go under `docs/benchmark/`, and `BENCHMARK.md` reports them.

**Tech Stack:** numpy (runtime dep already). Added to the `train` group: `matplotlib>=3.9` and `pyarrow>=17`; `huggingface_hub` is already there.

**Spec:** `docs/superpowers/specs/2026-11-01-tierwise-design.md` §5 (Evaluate, Calibration), §7 (Eval regression), §8 M5

## Dataset decision (made with the user)
| Dataset | License | Role | Cheap / strong pair | Quality signal | Cost |
|---|---|---|---|---|---|
| `routellm/gpt4_dataset`, our **test split** (hash-split, never trained on) | Apache-2.0 | **Headline numbers** | Mixtral-8x7B / GPT-4 | Cheap: `(mixtral_score − 1) / 4`. Strong: `1.0` (the judge's reference; this is an assumption and is stated in BENCHMARK.md) | Response and prompt length in chars / 4 × historical list prices |
| [`CARROT-LLM-Routing/SPROUT`](https://huggingface.co/datasets/CARROT-LLM-Routing/SPROUT), `test` split | **None stated** | Out-of-distribution check. Downloaded at eval time, not committed; only aggregate numbers are published, with a note | gpt-4o-mini / gpt-4o | The per-model `score` field (asserted to be in [0, 1]) | `num_input_tokens` / `num_output_tokens` × list prices |

Both pairs are older models, not tierwise's registry. The benchmark measures the *router's* ability to tell which prompts a cheap model handles, and that claim carries across models.

## Global Constraints
- Everything in the M3–M4 plans' Global Constraints still holds. In particular: ruff line length 100, strict mypy on `src/`, and CI runs `uv sync` (dev group only, no `model.onnx`, no network).
- **Sweep rule:** a prompt goes to the strong model iff `score >= t`.
  - Thresholds are every distinct score, plus `+inf`, which means all-cheap.
  - Ties go to the strong model.
- **Point metrics:**
  - `cost` is the mean per-prompt cost in USD.
  - `quality` is the mean per-prompt quality of the chosen model.
  - `quality_frac = quality / quality_all_strong`, and `cost_frac = cost / cost_all_strong`.
- **Headline metric:** `cost_saved_at(points, 0.95) = 1 − cost_frac` of the cheapest point with `quality_frac >= 0.95` (the `TODO(human)` decides interpolation; see Task 1). `None` if no point qualifies.
- **Random baseline:** `numpy.random.default_rng(0)` uniform scores.
- **Prices (USD per 1M tokens, input/output):**
  - GPT-4 (`gpt-4-1106-preview`) 10 / 30.
  - Mixtral-8x7B 0.60 / 0.60.
  - gpt-4o 2.50 / 10.00.
  - gpt-4o-mini 0.15 / 0.60.
  - Task 2 verifies these against provider pages or the RouteLLM paper and records the source in `evaluation/datasets.py` and BENCHMARK.md. A corrected price is a ruling, not a blocker.
- **Nothing from SPROUT is committed.** No rows, prompts or responses in the repo or in `docs/benchmark/*.json`, which hold aggregates only.

## Review Focus
1. **Ties and constant scores.** A scorer that returns the same value for every prompt (rules on short prompts often do) must give a two-point curve (all-cheap, all-strong) and not crash or divide by zero. Test in Task 1.
2. **Routing can beat all-strong.** On prompts where the cheap model answered better, `quality_frac` exceeds 1.0. The metric must handle that, with no clamp that hides it. When no point reaches the target (only possible with hand-built points or a target above 1), `cost_saved_at` returns `None`. Tests in Task 1 and Task 4.
3. **SPROUT rows missing a model or with an out-of-range score.** Missing rows are dropped and counted; an out-of-range score raises. Tests in Task 2.
4. **The hybrid must match production exactly.** It goes through `route()`, not a re-implementation. A test checks it against `route()` with a fake learned router (Task 3).
5. **Train/test leakage in the headline numbers.** The eval must read only the `test` split that `prepare_data` wrote. A test checks that the loader rejects a file whose prompts hash to a train split (Task 2).

## Decisions this plan makes (deviations from the spec text)
- **Package `evaluation/`, not `eval/`.** A package named `eval` shadows the built-in in any module that imports it. Cost if wrong: a rename.
- **No separate "learned + cache-aware selection" curve.** Both datasets are single-turn, where cache-aware selection picks the same model as cost-only selection. The M3 tests already cover cache-aware selection on conversations. Cost if wrong: one more scorer when a multi-turn dataset exists.
- **Registry `quality` is not calibrated from these benchmarks.** Neither dataset contains tierwise's registry models (Claude/GPT-5.x/Gemini 3). BENCHMARK.md reports SPROUT's per-model mean scores as a reference for each model generation, and the registry keeps its placeholders, labeled as such, until M9's shadow labels exist for our own models. Cost if wrong: registry quality values stay unvalidated for longer.
- **Critical set = the 9 `hard` prompts in `tests/router/labeled_prompts.jsonl`**, gated by routing through the shipped registry. A large-dataset "misroute" count can't be gated at zero: every operating point under 100% strong sends some weak-failing prompts to the cheap model. The large-set count is *reported* in BENCHMARK.md instead.
